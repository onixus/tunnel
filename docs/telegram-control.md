# Telegram-управление и панели через TrustTunnel

Установлен `vpn-telegram.service` на VPN-сервере. Используется существующий бот `@onixus_hui_bot` и владелец из прежнего `TELEGRAM_CHAT_ID` H UI. Токен и числовой ID хранятся только в `/etc/vpn-telegram/config.json`, root `0600`. Код — [vpn-telegram.py](../scripts/vpn-telegram.py), unit — [vpn-telegram.service](../examples/systemd/vpn-telegram.service).

В H UI `TELEGRAM_ENABLE=0`: старый polling отключён, чтобы не конкурировать за getUpdates. Старые уведомления H UI о входе также отключены. Почтовый мониторинг продолжает работать независимо.

Команды в личном чате:

- `/status`: службы, включая единую консоль, ресурсы, текущий выход, срок сертификата.
- `/panel`: кнопка единой HTTPS-консоли; `/panels` сохранён как совместимый alias.
- `/bans`: статистика Fail2ban для `sshd` и `vpn-web`.
- `/route`: кнопки основного/резервного выхода Hysteria; исключения RU/РФ/СНГ сохраняются.
- `/restart`: перезапуск Hysteria либо TrustTunnel.
- `/help`: справка.

Проверяются одновременно Telegram sender ID, chat ID и тип private. Чужие и групповые сообщения игнорируются. Изменение состояния требует одноразового подтверждения с TTL 120 секунд, повторные callback не исполняются. Произвольных shell-команд нет; разрешены только четыре фиксированных действия. Старые текстовые команды не исполняются после 180 секунд. Offset сохраняется до исполнения, чтобы перезапуск не повторил операцию; при сбое между сохранением и исполнением команду надо повторить. Сервис работает root, поскольку управляет systemd, Docker и переключателем маршрутов; защита токена и Telegram-аккаунта владельца критична.

Проверены четыре теста авторизации, подтверждений, их срока и повторов. На сервере подтверждены успешный getMe, активный polling, отсутствие рестартов/ошибок. После явного разрешения владельца тестовый отчёт успешно принят Telegram (message ID 9). Сквозное нажатие команды владельцем ещё не проверялось.

## Панели через TrustTunnel

При активном TrustTunnel:

- H UI: http://139.100.233.173:8081
- TrustTunnel: http://139.100.233.173:18082/admin/login

Через Hysteria сохраняются прежние адреса `10.254.77.1:8081` и `10.254.77.1:18082`. Пароли панелей обязательны.

Доступ разрешён UFW только с Docker bridge `br-c0195f42499e`, источник `172.18.0.0/16`, к двум указанным адресам/портам. Правила стоят перед общим запретом H UI. Порт 18082 на публичном адресе обслуживается socket-activated `systemd-socket-proxyd`, который пересылает на loopback 127.0.0.1:18082. Firewall закрывает внешний доступ; Docker publish остаётся loopback-only. При пересоздании Docker-сети может измениться bridge ID — тогда нужно обновить UFW-правила. Доступ имеют процессы этой Docker-сети; не подключайте к ней недоверенные контейнеры.

`allow_private_network_connections=false` сохранён: остальные приватные назначения не открывались. Проверка с .116 через SOCKS официального клиента TrustTunnel вернула HTTP 200 от обеих панелей; с onixus.ru вне TrustTunnel оба публичных порта завершились таймаутом. Если клиент исключает IP самого VPN-сервера из системного TUN-маршрута, используйте SOCKS через TrustTunnel либо доступ к панелям через Hysteria/SSH.

## Обслуживание

```sh
systemctl status vpn-telegram trusttunnel-panel.socket
journalctl -u vpn-telegram --since '10 minutes ago'
```

Остановить бота: `systemctl disable --now vpn-telegram`. Чтобы вернуть встроенного бота H UI, после остановки отдельного сервиса верните `TELEGRAM_ENABLE=1` в SQLite при остановленной H UI, затем запустите H UI. Не запускайте оба обработчика одного токена одновременно.

## Интеграция с единой консолью

[HTTPS-консоль](https://onixus-rf.duckdns.org/console/) показывает состояние
существующего бота и позволяет готовить Telegram-рассылки согласившимся
получателям. Новый polling-процесс не запускается; управляющие команды
существующего бота остаются доступны только владельцу. Адресат должен сначала
открыть бота и нажать Start. Токен в браузер не передаётся.
[Доставка и её ограничения](../server/console/README.md#delivery-and-telegram).

С 1 октября 2026 `/panel` открывает `https://onixus-rf.duckdns.org/console/`. Меню команд зарегистрировано в Telegram и проверено через `getMyCommands`. Новые проверки не отправляли сообщений владельцу. [Защита веб-входа](web-protection.md).

## Консоль из-под TrustTunnel

Публичный адрес onixus-rf входит в RU-диапазон `139.100.192.0/18`, поэтому relay
TrustTunnel отправляет запросы к консоли напрямую из контейнера на собственный
публичный IP. Docker DNAT для 443 не применяется к трафику с моста, пакет попадает в
INPUT, и UFW его отбрасывал (`UFW BLOCK SRC=172.18.0.2 DST=139.100.233.173 DPT=443`).
Через Hysteria консоль работала. С 2 октября 2026 добавлено узкое правило:

```sh
ufw allow in on br-c0195f42499e from 172.18.0.0/16 to 139.100.233.173 port 443 proto tcp
```

Как и для 8081/18082, при пересоздании Docker-сети ID моста меняется и правило надо
обновить.

## Telegram ID получателей

Чтобы получать конфигурации из консоли, пользователь открывает бота и отправляет
`/start` или `/id`. Посторонним бот отвечает **только** их собственным числовым ID
(не чаще раза в минуту, только в личном чате, где отправитель совпадает с чатом).
Управляющие команды по-прежнему доступны лишь владельцу. Тест:
[test-vpn-telegram.py](../tests/test-vpn-telegram.py).
