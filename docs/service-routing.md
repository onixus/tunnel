# Интерактивная карта и маршруты сервисов

Консоль управляет выходящим VPN-трафиком Hysteria 2 и TrustTunnel. Клиенты
R-TrustTunnel используют тот же endpoint TrustTunnel и не являются третьим
независимым сервисом. Системная таблица маршрутов, SSH, HTTPS-панель, почта и
Telegram не переключаются.

## Работа с картой

Нажмите на основной, резервный или прямой выход. Выберите сервисы, откройте
предварительный план и подтвердите переключение отдельной кнопкой. До
подтверждения конфигурация не меняется. План показывает исходный и конечный
выходы, необходимость переподключения и сервисы, которые останутся без изменений.

У каждого VPN есть три режима:

| Режим | Поведение |
|---|---|
| Общий маршрут | Следует выбранному общему выходу |
| Свой маршрут | Закреплён за основным или резервным выходом независимо от группы |
| Напрямую | Выходит через входной сервер, не следует переключению группы |

Снятый с выбора участник группы сохраняет **фактический** выход: консоль
переводит его в закреплённый или прямой режим. Это изменение политики без
перезапуска, если сам выход остаётся прежним. Уже закреплённый сервис не
перенастраивается при переключении другого сервиса. Нажатие на карточку сервиса
открывает отдельную настройку только для него.

Например: Hysteria можно направить через основной узел, TrustTunnel через
резервный. Либо оставить TrustTunnel напрямую и переключать только Hysteria.

Линии на карте показывают прочитанную конфигурацию, а не доказанную доступность
узлов. После постановки задания карта не рисует предполагаемый новый маршрут.
Результат появляется после перечитывания состояния. Неизвестная конфигурация,
неподготовленный адаптер и незавершённое восстановление явно блокируют управление.

## Область изменений и проверки

Карта меняет только последний catch-all Hysteria и соответствующий outbound.
Все исключения, включая нестандартные ACL, доступ к панелям и локальный DNS,
сохраняются в исходном порядке. Отдельный редактор исключений по-прежнему
проверяет защищённый префикс и запрещает замену неподдерживаемых правил.
На прямом выходе старый редактор исключений отключён: сначала выберите основной
или резервный выход на карте. Вернуться с прямого выхода также нужно через карту,
поскольку прежний CLI этот catch-all не распознаёт.

TrustTunnel использует штатный `forward_protocol.socks5` и локальный sing-box
relay в том же контейнере. Relay подключается к аутентифицированному SOCKS5
выходу по WireGuard. Пароли выхода не передаются в браузер или аргументы
процессов. Для TCP/UDP 53 сохраняется прямой путь к существующему перехвату DNS;
остальной трафик не имеет автоматического прямого fallback. Внешний DoH/DoT
не является обычным DNS на порту 53 и не получает этот обход.

Генератор `vpn.toml` подключает модуль маршрутизации при каждом запуске и
пересоздании конфигурации, в том числе после изменения пользовательских ключей.
Настройка не теряется при обычном перезапуске контейнера. TLS, запрет частных
адресов назначения и другие параметры endpoint не заменяются.

Перед переключением проверяется используемый выход. После изменения Hysteria
выполняется запрос через нативный Hysteria-клиент, после изменения TrustTunnel
через нативный клиент по **HTTP/2 и HTTP/3**. Оба запроса должны вернуть ожидаемый
IPv4. Это проверка VPN-подключения и HTTPS egress, не исчерпывающий тест всех
UDP-приложений. Выходные адреса в этой версии должны быть IPv4; адреса upstream
SOCKS5 в профилях должны быть буквальными IPv4 WireGuard, не произвольными URL.

## Обновление консоли

Требуется действующая установка из [unified-console.md](unified-console.md),
Python 3.11+ с PyYAML и cryptography, Docker и systemd. Сохраните резервную копию
и административный SSH-сеанс. Передайте на сервер актуальные каталоги `server`,
`deploy` и `scripts` из одной версии репозитория. Из корня репозитория:

```sh
sudo python3 deploy/install-console.py
```

Установщик обновляет отдельную консоль и точку входа локального агента.
Старые `agent.py` и CLI сохраняют прежнюю реализацию. Работающий контейнер
TrustTunnel этим установщиком не заменяется.
Новая консоль использует `routing_app:app`, агент `routing_agent.py`.
Остальные страницы, учётные записи, очередь и аудит остаются существующими.

Hysteria сразу доступна при распознаваемой конфигурации. TrustTunnel остаётся
на текущем маршруте и показывает причину недоступности переключения, пока не
подготовлен описанный ниже адаптер. Одна только новая кнопка не включает
маршрутизацию неподготовленного endpoint.

## Однократная подготовка TrustTunnel

Выполняется отдельно и явно, в согласованное окно обслуживания: замена образа
кратко переподключит клиентов. Установщик предназначен для исходного прямого
выхода и Compose `/opt/trusttunnel-web/compose.yaml`. Нестандартный источник
Compose или уже настроенный mount требует отдельной проверки оператора.

1. Подготовьте доверенный нативный `trusttunnel_client` в
   `/usr/local/bin/trusttunnel_client`, root:root, без записи для группы/остальных.
   Возьмите подходящий Linux-бинарник из официального релиза и отдельно проверьте
   происхождение и контрольную сумму.
2. Создайте отдельную действующую VPN-учётную запись для проверки. Сохраните её
   нативный TOML-профиль с проверкой TLS в
   `/etc/trusttunnel/routing-probe.toml`, root:root `0600`. Используйте SOCKS-профиль:
   профиль с TUN, отключением проверки TLS, selective mode или исключениями
   отвергается. Probe сам создаёт временный loopback SOCKS listener и по очереди
   проверяет HTTP/2 и HTTP/3. Временные файлы удаляются, секреты не печатаются.
3. Подготовьте Linux sing-box 1.11+ нужной архитектуры и **заранее проверенный**
   SHA256. Затем выполните:

```sh
sudo python3 deploy/install-trusttunnel-routing.py \
  --sing-box /root/staged/sing-box \
  --sha256 REPLACE_WITH_VERIFIED_SHA256
```

Установщик не скачивает исполняемые файлы. Он строит дочерний образ от точного
текущего image ID, проверяет ожидаемую точку интеграции генератора и валидирует
relay-конфигурацию staged-бинарником в изолированном контейнере без сети. Затем
подключает root-managed каталог и заменяет только сервис `trusttunnel-web`.
До и после замены выполняется нативная проверка прежнего прямого IPv4. При
ошибке восстанавливается предыдущий Compose и образ.

Каталог `/opt/vpn-console/trusttunnel-routing` имеет владельца root:10001 и
права `0750`, файл `trusttunnel.json` права `0640`. В контейнер каталог подключён
read-only как `/console-routing`. Подключайте **каталог, не отдельный файл**:
атомарная замена файла должна быть видна после перезапуска. Не копируйте
содержимое JSON в issues или журнал: оно может содержать SOCKS5 credentials.

После успешной установки обновите состояние консоли. Только тогда настройка
TrustTunnel становится доступной. Отдельно проверьте UDP-приложение, локальный
DNS-фильтр, блокировку частных сетей, перезапуск контейнера и перевыпуск ключа.
Удаление или ротация проверочной учётной записи требует обновить root-only
профиль; иначе переключение не пройдёт проверку.

### Последующие обновления образа

Не заменяйте адаптированный образ исходным upstream-образом. Новый пакет должен
содержать `app.trusttunnel_routing`, интеграцию в `write_vpn_toml` и совместимый
sing-box, сохраняя read-only mount. Подготовьте образ от проверенного нового
базового image ID с тем же build context из `build_context()` установщика,
проверьте его отдельно и установите оператором с сохранением mount и проверкой
нативного egress до и после. Сохраните предыдущий Compose для отката.
Не запускайте однократный установщик поверх уже настроенного mount.

Старый механизм обновления серверных компонентов через консоль не знает о новой
политике. После сохранения сервисной политики или подготовки адаптера такие
обновления блокируются с явным сообщением. Это предотвращает незаметную потерю
маршрутизации при замене образа. Обновления клиентских каналов не блокируются.

## Конкурентность, откат и восстановление

Preview ничего не применяет. Payload содержит ревизию всей наблюдаемой
конфигурации и политики. При изменении после preview необходимо прочитать новое
состояние и подтвердить новый план. Агент повторно проверяет ревизию после
preflight. Для CLI, Telegram и консоли используется общий
`/run/hysteria-exit-switch.lock`. Повтор HTTP-запроса с тем же request ID не
создаёт второе задание.

Перед первой записью сохраняется root-only журнал транзакции и запускается
systemd watchdog. Изменения нескольких сервисов компенсируются обратным
применением при ошибке, а не объявляются одной атомарной сетевой операцией:
между перезапусками возможен краткий смешанный маршрут. Восстанавливаются только
сервисы, к записи которых агент уже приступил. Откат проверяет старый egress.
Чужая конфигурация, изменённая вне операции, не перезаписывается автоматически.

Журналы: `/root/hysteria-route-backups/services/`. Незавершённая транзакция
отмечена `/opt/vpn-console/routing-pending.json`. Watchdog начинает восстановление
через 240 секунд и ждёт общий lock; после успешного commit он ничего не меняет.
Перезапуск агента также проверяет marker и восстанавливает незавершённое действие,
включая прерывание до запуска таймера. При неудаче агент продолжает отдавать
состояние, но новые изменения маршрутов заблокированы.

Для ручного повтора восстановления после проверки состояния, из SSH:

```sh
sudo python3 /opt/vpn-console/service_routes.py --restore \
  /root/hysteria-route-backups/services/REPLACE_WITH_JOURNAL_NAME.json
```

Не удаляйте marker ради разблокировки кнопки. Сначала проверьте конфигурации,
доступность прежних выходов и credentials probe; журнал может требовать
согласования с ручными изменениями оператора. Содержимое журналов конфиденциально.
Задание, прерванное перезапуском консоли, может остаться `unknown`, даже когда
watchdog уже восстановил сеть: состояние задания и восстановление сети различны.

## Проверки разработки и приёмка

Из корня репозитория:

```sh
python3 -m pip install pytest PyYAML cryptography fastapi httpx playwright
python3 -m pytest server/tests/test_service_routing.py server/tests/test_routing_api.py
python3 -m playwright install chromium
python3 -m pytest server/tests/test_routing_browser.py
node --check server/console/static/routing-ui.js
```

Новые unit/API-тесты используют поддельный транспорт и изолированную SQLite.
Браузерные тесты используют настоящие статические файлы репозитория и локальный
тестовый API, без доступа к VPN. Workflow сохраняет desktop/mobile screenshots.
Полный прежний `test_console.py` дополнительно требует checkout R-TrustTunnel
и собранный `rtrust-codec`; новые тесты его не заменяют.

Перед эксплуатацией проверьте на целевом сервере оба выхода, оба транспорта
TrustTunnel, Hysteria, DNS/UDP, сохранение маршрута при перевыпуске ключей,
отмену в UI и контролируемый отказ второго сервиса с восстановлением первого.
Результаты изолированных тестов не являются подтверждением live-деплоя.
