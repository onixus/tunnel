# Антибот-защита, капча и «отключите VPN»

Почему сайты с антибот-защитой (Cloudflare, Qrator, Akamai, reCAPTCHA/hCaptcha,
защита входа игровых аккаунтов, например ArenaNet) ломаются при включённом VPN,
и как это исправить, не трогая остальной трафик.

## Почему это происходит

Причины перечислены по весу. Обычно срабатывают первые две одновременно.

1. **Адрес дата-центра.** Если выход принадлежит хостинг-сети, антифрод-системы оценивают ASN и
   репутацию адреса; хостинг-адрес сам по себе даёт капчу, отказ во входе или
   «Отключите VPN». Серверные правила это не исправляют: нужен адрес другого
   типа.
2. **Смена адреса между входами.** При переключении выхода адрес меняется. Для сервиса это
   вход то из одной страны, то из другой. Защита входа (ArenaNet, Google,
   Microsoft, Steam) требует подтверждение по почте или блокирует вход.
3. **Страница и капча уходят с разных адресов.** `.ru`/`.рф` и GeoIP СНГ идут
   напрямую, остальное в выход. Если сайт и его капча или API попадают в разные
   правила, токен проверки выдан одному адресу, а предъявлен с другого.
   Поэтому домены капчи нельзя выносить отдельным правилом: сайт и всё, что он
   загружает для входа, должны уходить через один выход.
4. **Утечка IPv6 или WebRTC.** Если сервер использует только IPv4, а профиль
   клиента не забирает IPv6 в туннель, сайт видит домашний IPv6 провайдера и
   IPv4 выхода одновременно. Это сильный сигнал прокси.
5. **Несовпадение окружения.** Часовой пояс и язык браузера (Москва, ru-RU) при
   адресе в другой стране. Вес небольшой, но добавляется к остальным.

## Решение: отдельный «чистый» выход для чувствительных сайтов

Общий маршрут не меняется. Короткий список доменов уходит через постоянный
адрес резидентного типа (статический ISP-прокси, то есть адрес домашнего или
бизнес-провайдера). Остальной трафик идёт как раньше.

```
Клиент ─▶ ВХОД (ACL Hysteria) ─┬─ .ru/.рф, СНГ ─▶ напрямую
                              ├─ clean(suffix:arena.net …) ─WG─▶ РЕЗЕРВ :1081 ─▶ ISP-прокси ─▶ сайт
                              └─ всё остальное ─▶ выбранный выход
```

Почему именно так:

- Адрес один и не меняется при переключении выходов. Сервисы видят одно
  «домашнее» место, повторные подтверждения входа прекращаются.
- Цепочка идёт через резервный выход по существующему WireGuard. Учётные данные
  прокси не уходят с российского адреса открытым SOCKS5, а Hysteria и
  TrustTunnel получают обычный SOCKS5-профиль с IPv4 WireGuard, как у
  основного и резервного выходов.
- Исключение `clean(...)` задаётся в обычном редакторе исключений консоли.
  TrustTunnel повторяет его через relay автоматически, как и остальные
  исключения ([service-routing.md](service-routing.md#политика-trusttunnel-relay)).

Выбор поставщика. Нужен **статический ISP-прокси** (один постоянный адрес,
трафик без поминутной тарификации, SOCKS5 с логином). Ротируемые резидентные
прокси не подходят: адрес меняется, это ломает вход так же, как переключение
выходов. Страну выбирайте одну и постоянно, ту, где обычно «живёт» аккаунт.
Многие такие прокси не пропускают UDP: QUIC/HTTP3 через них не работает,
браузер и лаунчеры откатываются на TCP.

Бесплатная замена для проверки идеи: Cloudflare WARP на резервном выходе в том
же слоте (`:1081`). Сайты за Cloudflare обычно пропускают WARP без капчи, но
часть сервисов, включая игровые, помечает эти адреса как VPN. Как постоянное решение для входа в
аккаунты WARP хуже статического ISP-адреса.

## Какие домены отправлять

Только сайты, где ломается вход или капча, целиком, со всеми их доменами
авторизации. Не добавляйте домены капч (`recaptcha.net`, `hcaptcha.com`,
`challenges.cloudflare.com`) отдельно от сайтов: см. причину 3.

| Сервис | Правила |
|---|---|
| ArenaNet / Guild Wars 2 | `suffix:arena.net`, `suffix:arenanet.com`, `suffix:arenanetworks.com`, `suffix:guildwars2.com` |

Правило `clean(...)` ставьте выше `.ru`/`.рф` и GeoIP СНГ, иначе CDN сервиса с
российским адресом уйдёт напрямую.

Без «чистого» выхода часть пользы даёт закрепление тех же доменов за одним
выходом (`primary(suffix:arena.net)` и т. д.): адрес перестаёт прыгать при
переключении, хотя остаётся хостинговым.

## Установка

Выполняется оператором в окно обслуживания. Ниже шаблоны; секреты только
локально.

1. **Резервный выход.** Второй экземпляр sing-box по
   [examples/sing-box-clean-exit.json](../examples/sing-box-clean-exit.json):
   SOCKS5 с логином на `10.254.78.2:1081`, выход в ISP-прокси. Порт `1081`
   открыть в firewalld только для `10.254.78.1` в зоне WireGuard. Проверка на
   самом резервном узле:
   `curl --socks5-hostname USER:PASS@10.254.78.2:1081 https://ifconfig.me`
   должен вернуть адрес ISP-прокси.
2. **Профиль выхода.** Добавить `clean` в `/etc/hysteria/exits.json` по
   [examples/hysteria-exits.json](../examples/hysteria-exits.json) с
   `expected_ip` адреса прокси. `hysteria-exit-switch check` начнёт проверять и
   его.
3. **Outbound Hysteria.** Добавить outbound `clean` (socks5 `10.254.78.2:1081`)
   в конфигурацию H UI, как в
   [examples/hysteria-server.yaml](../examples/hysteria-server.yaml).
4. **Исключения.** В консоли, раздел «Исключения Hysteria», выход «Чистый IP»,
   домены из таблицы выше. Консоль не даёт сохранить `clean`, пока нет его
   профиля. Общим выходом `clean` выбрать нельзя.

Откат: удалить правила `clean(...)` в консоли. Профиль и outbound без правил
ни на что не влияют.

## Проверка на клиенте

С включённым VPN, по очереди для Hysteria и TrustTunnel:

- https://browserleaks.com/ip — на обычном сайте адрес выхода, IPv6 нет или он
  тоже от VPN.
- https://browserleaks.com/webrtc — нет домашнего адреса провайдера.
- Вход в сервис из списка. Адрес, который видит сервис, должен совпадать с
  `expected_ip` профиля `clean`.
- Mac (Hiddify) и Windows: в профиле включён TUN с IPv6-маршрутом в туннель или
  IPv6 отключён на интерфейсе. Linux-профиль из
  [examples/sing-box-client.json](../examples/sing-box-client.json) уже
  заворачивает IPv6 в TUN и резолвит только IPv4.

Часовой пояс браузера под страну прокси менять не обязательно. Если сервис всё
ещё просит подтверждение, один раз подтвердите вход: при постоянном адресе
повторов быть не должно.

## Ограничения

- Сайты, которые блокируют любые прокси, включая резидентные, этим не
  открываются. Для них остаётся отключение VPN или правило `local(...)`, если
  сайту нужен российский адрес.
- Работоспособность `clean` зависит от резервного выхода и WireGuard
  `wg-reserve`. При их отказе сайты из списка не открываются; автоматического
  отката на другой выход нет, как и для остальных исключений.
- Через `clean` идёт весь трафик сервиса, включая игровые серверы и загрузки
  клиента. Это добавляет задержку и объём через прокси.
